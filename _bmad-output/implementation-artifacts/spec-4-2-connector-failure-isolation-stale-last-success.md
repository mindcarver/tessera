## Intent

**Problem:** When a Connector fails today (root moved, permission changed, format unsupported, scan crashed), the failure IS already isolated per-source and the previous successful generation stays queryable — but the user cannot see WHY a Source is degraded, cannot tell that the results they are seeing are stale (from an older success while the source is currently unavailable), and the cause collapses to a generic string. `HealthState` is a 4-state enum with no structured cause; a deleted root and a permission error render identically. FR-13/CAP-9 require the failed Source to show a structured cause (path missing / permission denied / format unsupported / scan failed), last-success time, and an explicit stale marker.

**Approach:** Add a stable structured `HealthCause` taxonomy (`path_missing | permission_denied | format_unsupported | scan_failed | none`), classify I/O errors at the adapter/root-validation boundary by `io::Error::kind()` so the four categories are genuinely distinguishable (not string-suggested), persist `health_cause` on the `source_registry` row alongside `health_state` (paying the cause/timestamp debt the 1.3 design note explicitly deferred to "Story 1.8 / 4.x"), and surface `cause` (structured) + `stale` (derived) on the inventory endpoint. Keep `last_success_at` derived (it already survives half-failures — the load-bearing NFR-9 property). Derive `stale = (health in {degraded,error}) AND active_generation exists`. The existing failure-isolation machinery (fencing-token CAS, single-owner gate, generation switch) is reused verbatim — this story makes failure VISIBLE, not possible.

## Boundaries & Constraints

**Always:**
- Failure isolation is preserved by construction — this story ADDS visibility, it must not touch the fencing-token CAS, the single-owner gate (`reserve_run`), the generation switch (`commit_cas`), or boot recovery. The previous active generation stays queryable while a scan/reconcile is in progress (NFR-12) and after a failed scan (NFR-9) — verified, not rebuilt.
- The cause taxonomy is the four architecture-mandated categories plus `none`: `path_missing` (root gone / not-a-dir / `ErrorKind::NotFound`), `permission_denied` (`ErrorKind::PermissionDenied`), `format_unsupported` (parse/canonicalize failure), `scan_failed` (everything else: mid-scan read errors that aren't path/perm, `dirty_after_validation`, `commit_cas` loss, internal). `none` means healthy or never-probed.
- Cause classification happens at the I/O boundary by inspecting `io::Error::kind()` (NOT by string-matching messages — messages are locale/OS-dependent and AD-13-forbidden to surface anyway). `NotFound` → `path_missing`; `PermissionDenied` → `permission_denied`; any other kind at a root/dir-resolution site → `scan_failed`; a parse/canonicalize failure → `format_unsupported`.
- `health_cause` is persisted on the `source_registry` row (new column, v5 migration) and written at EVERY `set_health` site — success writes `(Healthy, none)`, root-validation failure writes `(Degraded, path_missing|permission_denied|scan_failed)`, parse failure writes `(Degraded, format_unsupported)`, dirty-after-validation/internal write `(Error, scan_failed)`. The cause is cleared (set to `none`) on the next successful scan. Persisting — not deriving — is required because the root-validation failure path precedes `begin_run` and therefore writes NO `scan_runs` row, so the cause cannot be recovered from `scan_runs.error_code` for the single most important failure mode (root gone).
- `last_success_at` stays DERIVED from `scan_runs` (`MAX(finished_at) WHERE state='succeeded'`) — it already correctly survives arbitrary subsequent failures and is the load-bearing NFR-9 invariant. Do NOT duplicate it onto the source row.
- `stale` is DERIVED at read time: `stale = (health_state in {degraded, error}) AND active_generation IS NOT NULL`. It means "an older successful generation is still serving results while the source currently fails to refresh it". A source that is degraded with NO active generation is `unavailable`, not `stale` (already modeled by `SourceQueryStatusKind::Unavailable`).
- The cause is redacted and safe (AD-13): the persisted code is a stable category enum, never a path/body/credential.
- `cause` and `latest_error` are INDEPENDENT fields answering different questions, and MUST NOT be collapsed: `latest_error` = "what happened to the most recent run" (keeps its current derivation from `scan_runs.error_code` for a `Failed` latest run, PLUS the existing `"Tessera could not access this source."` fallback when `health_state == Degraded` and the latest run is not `Failed` — e.g. the run-less root-validation path); `cause` = "why is the source's health degraded" (the new structured field, persisted on the source row). A cancelled rescan sets `latest_error = "The last rescan was cancelled."` but leaves `cause` unchanged (cancel is not a health transition); a root-deleted scan sets `cause = path_missing` and, because there is no failed run row, `latest_error` falls back to the Degraded string. Keeping `latest_error`'s derivation untouched means every existing pinned string (`inventory.rs:43,111,176,287`) stays green with zero rewrite.
- DTO change is additive and confined to `SourceInventory` (where `last_successful_scan` + `latest_error` already live): add `cause: Option<HealthCause>` (structured) and `stale: bool`. The bare `Source` DTO's WIRE shape (`GET /api/sources`) and `ScanStatus` (`GET /api/scan/status`) are NOT changed — the inventory endpoint is the health surface. The `Source` Rust struct does gain a `#[serde(skip)] health_cause` field to round-trip the persisted column (mirroring how `fingerprint` is already a `#[serde(skip)]` internal field on `Source`); because it is skipped, the wire shape is byte-identical and no frontend/TS-mirror change is required.

**Block If:** None. (The four cause categories and their mappings are fixed by the architecture; no tunable requires human input.)

**Never:**
- Never change the fencing-token CAS, `commit_cas`, `reserve_run` single-owner gate, `recover_stale_runs`, or the begin_run → run_pipeline → commit_cas mutation path. Failure isolation is a reused invariant, not rebuilt.
- Never persist `last_success_at` on the source row or add any timestamp column. The 1.3 "no timestamps on source rows" design note is preserved; `health_cause` is a categorical code, not a timestamp, and is the explicitly-deferred-to-4.x cause debt. (The rebuild-clears-scan_runs interaction with derived last_success is Story 4.4's concern.)
- Never classify cause by string-matching OS error messages, file paths, or adapter output. Only `io::Error::kind()` (for I/O failures) and the existing `ScanError` variant (for non-I/O failures like `DirtyAfterValidation`) feed the classification.
- Never build degraded-state recovery UI, path-change re-discovery, rebind, or full-index rebuild — those are Stories 4.3 and 4.4. This story surfaces cause + stale; it does not act on them.
- Never change the search/browse query SQL, cursor contract, `SearchEmptyState`/`BrowseEmptyState` derivation, or `SourceQueryStatusKind` sidecar. The three-way empty/unavailable distinction already exists; this story adds tests that a stale source still serves its older results (not empty) while an unavailable source still surfaces `SourceUnavailable`.
- Never add long-lived SSE/streaming for health. The existing finite-snapshot inventory + scan-status polling surfaces carry the new fields.
- Never change the `Source` DTO's WIRE shape, `ScanStatus` DTO, `BrowsePage`/`SearchPage` contract, or any frontend artifact. The new `#[serde(skip)] health_cause` field on the `Source` struct is internal-only (same precedent as `fingerprint`); the inventory endpoint is the only surface that emits `cause`+`stale`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|---------------|----------------------------|----------------|
| Root deleted between scans | Confirmed source, active generation exists; root path no longer resolves (`ErrorKind::NotFound` at canonicalize) | Scan fails BEFORE begin_run (no run row); `set_health(Degraded, path_missing)`; active generation preserved; inventory row: `health=degraded`, `cause=path_missing`, `last_success_at=<old>`, `stale=true` | Cause persisted on source row (the run-less failure path) |
| Root permission revoked | Confirmed source; `canonicalize` or `read_dir` returns `ErrorKind::PermissionDenied` | Scan fails; `set_health(Degraded, permission_denied)`; active generation preserved; inventory: `cause=permission_denied`, `stale=true` | Distinguished from path_missing by io kind |
| Unreadable dir inside root (e.g. `rollout_summaries/` perm-denied) | `read_dir` on a subdir returns `PermissionDenied` mid-enumeration | Run row created (begin_run already happened), marked `failed` with `error_code='enumeration_failed'`; `set_health(Degraded, permission_denied)` | Cause from io kind at the enumeration site |
| Format unsupported | An allowlisted Markdown file fails to decode/canonicalize | Run `failed` with `error_code='parse_failed'`; `set_health(Degraded, format_unsupported)` | Distinct category from I/O failures |
| Generic scan failure (read error mid-scan, dirty_after_validation, internal) | File read returns non-NotFound/non-PermissionDenied io error; or manifest drift; or SQLite error | Run `failed`; `set_health(Error|Degraded, scan_failed)` | Catch-all; does not masquerade as path/perm/format |
| Successful rescan after a failure | Previously degraded source; rescan succeeds | `commit_cas` activates new generation; `set_health(Healthy, none)` — cause CLEARED; `stale=false`; `last_success_at` advances | Cause cleared so a recovered source shows no stale cause |
| Degraded source with NO active generation (never succeeded) | Source confirmed, first scan fails | `health=degraded`, `cause=<category>`, `active_generation=None`, `stale=false` (no older results to be stale); `SourceQueryStatusKind=Unavailable` | `stale` requires an active generation |
| One source down, others healthy | Source A failed (degraded, stale); Source B healthy | Inventory returns BOTH rows; A carries `cause`+`stale=true`+`last_success_at`; B unaffected; search across both returns B's current results + A's older (stale) results; query sidecar flags A `Degraded` | Per-source isolation (existing) verified at the new surface |
| Half-failed scan (failed mid-stage) | Run reaches `staging` then fails | Previous active generation preserved (NFR-9); run `failed`; `set_health(Degraded/Error, <category>)`; `stale=true`; `last_success_at` unchanged | Existing generation-switch invariant; new cause+stale surface |
| Boot recovery of a stale run | Crash left a run in `staging`/`committing` | `recover_stale_runs` flips to `failed`/`stale_recovered` (existing); health+cause set on next scan or via the recovery path | Recovery path must not leave cause stale relative to health |
| Never-probed source | Newly confirmed, no scan yet | `health=unknown`, `cause=none`, `last_success_at=None`, `stale=false` | Defaults from migration + enum |
| Cancelled rescan | User cancels an in-flight rescan | Existing cancel path; health NOT changed by cancel (`Cancelled` maps to `Unknown` health, existing); `cause` left as-is (cancel is not a failure cause); stale unchanged | Cancel is not a health-transition |

**Acceptance Criteria:**
- Given a confirmed source with an active generation whose root is deleted, when a rescan/reconcile is attempted, then the scan fails BEFORE begin_run (no run row), the previous generation remains queryable, and the inventory row reports `health=degraded`, `cause=path_missing`, `last_success_at=<the prior success>`, `stale=true`.
- Given a confirmed source whose root permission is revoked, when a scan is attempted, then the failure is categorized `cause=permission_denied` (distinct from `path_missing`), health is `degraded`, and the older active generation stays queryable with `stale=true`.
- Given a confirmed source whose allowlisted artifact fails to canonicalize/parse, when a scan is attempted, then `cause=format_unsupported` is persisted and surfaced, distinct from the I/O categories.
- Given a confirmed source that failed (degraded, stale) and is then successfully rescanned, when the rescan commits, then `health=healthy`, `cause=none`, `stale=false`, and `last_success_at` has advanced — a recovered source shows no stale cause.
- Given two confirmed sources where source A's scan fails and source B's succeeds, when `GET /api/inventory` is called, then BOTH rows return; A carries its `cause` + `stale=true` + `last_success_at`; B is unaffected (`cause=null, stale=false`); and a cross-source search returns B's current results alongside A's older (stale) results without error (NFR-8).
- Given a half-failed scan (reaches staging then fails), when it fails, then the previous active generation is preserved byte-for-byte (NFR-9), the failed run row carries its `error_code`, and the source row carries the matching structured `cause` + `stale=true`.
- Given a source that is degraded but has NO active generation (first scan failed), when its inventory row is read, then `stale=false` (no older results to be stale) and `cause=<category>` — it is `unavailable`, not stale.
- Given the full test suite, when `cargo test --manifest-path server/Cargo.toml` runs, then all pre-existing tests stay green (the `SourceInventory` DTO change is additive; `latest_error` strings are preserved) and the new 4.2 tests pass.

## Design Notes

- **Why persist `health_cause` rather than derive it.** The single most important Connector failure — root deleted — fails at `policy::canonicalize_root` BEFORE `begin_run`, so it writes NO `scan_runs` row. Deriving cause from `scan_runs.error_code` (the current `latest_error` strategy) therefore returns `None` for exactly the failure that matters most, which today papers over with a generic `"Tessera could not access this source."` fallback whenever `health_state == Degraded`. Persisting `health_cause` on the `source_registry` row — written at the same `set_health` call sites — makes every failure category recoverable regardless of whether a run row exists. This pays the debt the 1.3 design note (`domain/source.rs:27-30`) explicitly deferred: "Source rows carry no timestamps … last-scan / last-error times belong to Story 1.8 / 4.x." `health_cause` is a categorical code (not a timestamp), so it does not violate the "no timestamps / no `chrono`" rule.
- **Why `last_success_at` stays derived.** `scan_store.last_successful_finished_at` (`MAX(finished_at) WHERE state='succeeded'`) already survives arbitrary subsequent failures by construction — that IS the NFR-9 invariant, and it is already tested (`inventory_keeps_last_success_and_omits_limited_coverage_count`). Duplicating it onto the source row would create a second source of truth that can drift. The 4.4 rebuild-clears-`scan_runs` interaction is 4.4's concern (after a rebuild the source is freshly successful, so `None`→"just rebuilt" is honest).
- **Why `stale` is derived, not persisted.** `stale = (health in {degraded,error}) AND active_generation IS NOT NULL` is a pure function of two fields that already exist and are kept coherent by the generation switch. Persisting it would add a third field to keep coherent with no gain. The derivation matches the existing query-sidecar semantics: `SourceQueryStatusKind::Degraded` (`application/query.rs:534-557`) already means exactly "active generation exists + health is Error/Degraded or latest run failed" — `stale` is the inventory-level spelling of the same fact.
- **Why split `EnumerateError::RootUnresolvable`.** The architecture mandates the cause "distinguish at minimum: path missing, permission denied, format unsupported, scan failed". Today `RootUnresolvable` collapses `ErrorKind::NotFound` and `ErrorKind::PermissionDenied` into one variant, so no downstream mapping can tell them apart. Classifying at the I/O boundary by `io::Error::kind()` is the only OS-locale-independent, redaction-safe way to make the distinction faithful (string-matching OS messages is forbidden by AD-13 and brittle). The same classification is applied at the mid-scan `read_verified` site for `ReadFailed`.
- **`cause` and `latest_error` are independent, not unified.** They answer different questions: `latest_error` = "what happened to the most recent run" (cancelled / drift / read-failed / generic), derived from `scan_runs.error_code`; `cause` = "why is the source's health degraded" (path_missing / permission_denied / format_unsupported / scan_failed), persisted on the source row. Unifying them would break the existing pinned strings (`inventory.rs:43,111,176,287`) AND erase information: a cancelled rescan sets `latest_error="The last rescan was cancelled."` but leaves `cause` untouched (cancel is not a health transition), while a root-deleted scan sets `cause=path_missing` but has no failed run row for `latest_error` to derive from (so `latest_error` falls back to the Degraded string). Keeping them independent means zero rewrite of existing tests and faithful semantics for both.
